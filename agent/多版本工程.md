# SlimefunHelper 多版本工程速查

本项目用 **`fabric-mod-template` 的预处理器方案** —— 这是 **Fallen-Breath** 个人维护的社区模板
（<https://github.com/Fallen-Breath/fabric-mod-template>），**不是** fabricmc 官方提供的：
一条分支、**一份源码**，同时构建 **26.1.2** 与 **26.2**。
不要按版本开分支、也不要维护两套源码树。

## 1. 目录与版本清单

| 路径 | 作用 |
|---|---|
| `settings.json` | 目标版本清单（`["26.1.2", "26.2"]`），是**唯一**的版本来源 |
| `settings.gradle` | 按这份清单为每个版本生成子工程：目录 `versions/<版本>/`，构建脚本统一指向根 `common.gradle` |
| `common.gradle` | 所有版本**共用**的构建逻辑（依赖、loom、shadowJar、AW、publishing…） |
| `versions/<版本>/gradle.properties` | 该版本的差异项（MC 版本、Fabric API、meteor、baritone…） |
| `versions/<版本>/overrideList.accesswidener` | **每版本一份** AW |
| `versions/mainProject` | 哪个版本的源码就是 `src/` 原文（本项目 = `26.2`） |
| `versions/mapping-26.1.2-26.2.txt` | 版本之间的改名映射表 |
| `src/` | **唯一的源码树**。其它版本由预处理器生成到 `versions/<版本>/build/preprocessed/main/java` |

## 2. ⭐ `//#if` / `//$$` 怎么写（最容易搞错）

```java
//#if MC >= 26.2
<26.2 的代码，正常书写>
//#else
//$$ <26.1.2 的代码，用 //$$ 注释掉>
//#endif
```

**规则：`mainProject` 那一版的代码不加 `//$$`。**

- `versions/mainProject` 指定哪一版**直接编译 `src/` 原文** → 它的代码必须能原样编译
- 本项目 `mainProject = 26.2` → **26.2 正常写、26.1.2 用 `//$$` 注释掉**
- 预处理器激活某分支时会去掉该分支的 `//$$` 前缀，未激活的分支行保持注释

其它注意：

- **`//$$` 里不能再嵌套 `//#if`**（预处理器不支持嵌套）
- 标记行可以缩进
- 条件可以写版本号字面量 `//#if MC >= 26.2`，也可以写数值 `//#if MC >= 260200`
  （节点值：`26.1.2 → 260102`、`26.2 → 260200`）
- `link` 的方向是「旧 → 新」：`mc2612.link(mc262, ...)`

> 看别的项目（如 LiteFetch）时先确认它的 `mainProject` 是哪一版 ——
> 如果对方是**最老**的版本当 mainProject，方向正好相反（`//#else` 那支才不加 `//$$`）。

## 3. 版本差异的三层处理（优先级从高到低）

能靠上层解决就别往下走：

| 层 | 什么时候用 | 例子 |
|---|---|---|
| **映射表** | 类改名、**同一宿主上**的方法改名 | `EntityType` → `EntityTypes`；`GameRenderer.getMainCamera()` → `mainCamera()` |
| **工具方法** | 宿主类变了 / 方法变字段 / 形态不同 | `ClientUtils.getScreen(mc)`：26.2 是 `mc.gui.screen()`、26.1.2 是 `mc.screen` |
| **逐处 `#if`** | 剩下零散的差异 | mixin 注解里的目标、个别 API 变更 |

映射表**一行能顶几十处，优先用它**。它只支持「就地改名」，宿主类变了表达不了。

`ClientUtils` 目前封装了：`getScreen` / `getOverlay` / `setScreen` / `getChat` /
`getMainRenderTarget` / `openChatScreen` / `isPlayerOnline`（各带无参重载）。
条件标记只写在方法体内部，业务代码两边共用同一份调用 —— **新遇到宿主差异时也照这个模式加方法**。

## 4. `versioned/` 层

`me.matl114.versioned` 是**跨版本 API 的适配层**：

- `versioned/api/` —— 各版本共用的接口/抽象类型（如 `VDrawContext`、`MatrixStack`）
- `versioned/impl/*_v1_21_11` —— 按版本给出的具体实现

业务代码只依赖 `api`，具体实现在各版本里挑。**不要**在业务代码里直接写版本条件去 new 具体实现。

> 命名提醒：`MatrixStack`、`VDrawContext` 这一层自己的类名和原版不同，
> 看到 `V` 前缀或不确定的名字，先去 `versioned/api` 找，别当成原版 API。

## 5. mixin 注解是重灾区

`@Inject(method = "...")`、`@At(target = "...")`、`@WrapOperation(method = "...")` 里的都是**字符串**：
javac 不校验，**只有进游戏、mixin 真正 apply 时才会以 `InvalidInjectionException` 炸**。

跨版本改 mixin 时，下面三类差异都要查，**别只看方法名**：

- **方法名 / 描述符**：`create(Level, EntitySpawnReason)` ↔ `create(Level, EntitySpawnRequest)`
- **handler 的 Java 参数表**：方法名改对了、参数表没改**照样炸**
  （例如 26.1.2 的 `renderTex` 末参是 `MultiBufferSource`，26.2 的 `submitBlockSprite` 是 `SubmitNodeCollector` 且多一个 `int`）
- **`@At(ordinal = N)`**：数的是**字节码里匹配指令的序号**，换了 target 就得重数；
  FIELD 的 ordinal 把 getfield 和 putfield **一起**编号

校验手段（按性价比排序）：

1. 跑 `./gradlew :26.1.2:preprocessCode` 生成源码，然后对**预处理产物**做 IDE 语义分析 ——
   Mixin 插件能把上面三类都报出来（`Cannot resolve method` / `Cannot resolve target reference` /
   `Method signature does not match expected signature`）。**别对着 `src/` 猜 26.1.2 的问题。**
2. 人工核对生成产物：每处都应是「26.2 版带 `//$$` / 26.1.2 版生效」
3. `@At(ordinal = N)` 用官方 jar 的 `javap -c -p` 数，**源码里数不准**

## 6. 常用命令

```bash
./gradlew buildAndGather          # 一次构建所有版本，jar 汇总到根 build/libs
./gradlew :26.2:build             # 只构建某一版
./gradlew :26.1.2:preprocessCode  # 只重新生成 26.1.2 源码（不编译，排查用）
./gradlew client262               # 起 26.2 客户端
./gradlew client2612              # 起 26.1.2 客户端
```

- 运行目录：`run/<MC版本>/`（由根 `build.gradle` 的 `loom.runs.*.runDir` 决定）
- ⚠️ **不要跑不带前缀的 `runClient`** —— Gradle 会在**每个**含该任务的子工程里各跑一次，
  两个客户端会同时启动。同理，IDEA 里用自动生成的 `Minecraft Client (:26.2)` / `(:26.1.2)`，
  别用从根工程建的 Gradle 任务配置

## 7. 坑（都是会浪费半天的）

| 坑 | 说明 |
|---|---|
| **不能用 spotless / palantir-java-format** | 它会在 `//` 后插空格、把 `//$$` 行折行 → 预处理器标记**全部失效**，生成的源码变成语法错误 |
| **`//$$` 别经过会解释 `$` 的字符串 API** | JS `String.replace` 的替换串、PowerShell `[regex]::Replace` 都把 `$$` 当转义 → 写成 `//$`，那行变成普通注释、方法因此缺少 return |
| **任务名不带前缀会命中所有子工程** | `gradlew runClient` 会选中 `:26.1.2:runClient` **和** `:26.2:runClient`；用 `gradlew :26.2:runClient` 或便捷任务 |
| **只在单版本存在的类不能 import** | import 是**全文件**生效的。例如 `MultiBufferSource` 只有 26.1.2 有 → 在 `//$$` 分支里**写全限定名**，加 import 会打断 mainProject 的编译 |
| **判某个类是否存在，用 jar 条目表** | `jar tf minecraft-merged.jar`；**别用 `javap` 的报错文本判**（会给出错误答案） |
| **javac 默认只报前 100 条错误** | 多版本适配时后面的差异会被挡住 → `common.gradle` 已加 `-Xmaxerrs 10000` |
| **正式产物必须走 shadowJar** | 否则打进去的依赖不全，装进启动器会 `NoClassDefFoundError` |
| **依赖集合用 `shade` 配置** | 不能用 `runtimeClasspath`（里面有 dev-only 的 baritone，会与正式 baritone 冲突） |

## 8. 加一个新版本要动什么

1. `settings.json` 的 `versions` 加一项
2. `versions/<新版本>/gradle.properties`（MC 版本与各依赖版本）
3. `versions/<新版本>/overrideList.accesswidener`（拷一份再按需改）
4. 根 `build.gradle` 的 `preprocess` 块加一个 `createNode`，并用映射表 `link` 到已有节点
5. 编译，把暴露出来的 API 差异按 §3 的三层处理掉
