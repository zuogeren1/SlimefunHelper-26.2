# SlimefunHelper 项目总述

## 1. 项目定位

**SlimefunHelper** 是一个面向 Minecraft **Fabric** 的客户端模组,为粘液科技(Slimefun)游玩、普通生存、
服务器探索和开发调试提供便利功能。

本项目从 `SlimefunHelper-1.21.11` 移植而来,现在**同时维护两条分支**:

| 分支 | Minecraft | 说明 |
|------|-----------|------|
| `26.2` | 26.2 | 最早的移植线 |
| `26.1` | 26.1.2 | 从 26.2 回退适配而来,复用同一套源码结构 |

两条分支共用本文档;模组版本号沿用上游 `1.1.6.3`,同一分支上的修复追加 `-fixN`。

## 3. 构建与产物

```bash

# 只编译(不足以验证 mixin/打包问题)
./gradlew compileJava
```

- 构建产物:**`build/libs/SlimefunHelper-<MC版本>-<mod版本>.jar`**(fat jar,已内嵌 snakeyaml / netty-handler 等)

## 5. 核心子系统

### 5.1 模块系统(`BaseModule`)
所有功能都写成 `BaseModule` 子类,靠 `ModuleManager` 注册、靠 `FlagRef` 开关。
事件的注册、命令的注册、热键的绑定都走基类提供的方法,这样模块禁用/移除时能自动清理。
详见 `模块.md`。

### 5.2 事件系统(`Listener` / `RenderListener`)
全局事件总线。所有通道都是 `ListenerPoint`,通过 `Listener.getXxx()` 静态 getter 拿到,
再用 `registerListener(channel, handler)` 挂上去。通道带 `canCancel` / `canModifyContext` 属性,
网络包还能按包类型 `getChannel(Class)` 精确分发。详见 `事件.md`。

### 5.3 命令系统(`MainCommand` / `AbstractMainCommand`)
树形子命令 + 强类型参数 + tab 补全 + 中文错误提示。
模块在 `registerAll()` 里用 `registerCommandBootstrap(this::bootStrapXxx)` 挂上自己的命令树。
详见 `命令.md`。

### 5.4 GUI 组件库(`DrawableWidget`)
一套自绘组件,可以塞进任意 `Screen`。容器(`SubScreenWidget`)负责坐标变换、层级与事件分发,
`RenderHandler` 负责画,`ElementHandler` 负责响应。详见 `GUI.md`。

### 5.5 配置系统(`Config` / Ref)
配置文件放在 `config/sfhelper-configs/*.yml`,每一项是一个 `Ref`:
`FlagRef` / `IntRef` / `DoubleRef` / `FloatRef` / `LongRef` / `StringRef` /
`EnumRef` / `KeyBindRef` / `ListRef` / `MapRef` / `NBTRef` / `ObjectRef`。

`Configs` 里预定义了各分组配置文件:

| Config 常量 | 文件 |
|-------------|------|
| `MINE_CONFIG` | `mine.yml` |
| `CHAT_CONFIG` | `chat.yml` |
| `RENDER_CONFIG` | `render.yml` |
| `COMBAT_CONFIG` | `combat.yml` |
| `INV_CONFIG` | `inv.yml` |
| `MOV_CONFIG` | `mov.yml` |
| `INTERACT_CONFIG` | `interact.yml` |

| `SLIMEFUN_CONFIG` | `slimefun.yml` |

| `EXTRA_CONFIG` | `test.yml` |
| `MISC_CONFIG` | `misc.yml` |
| `TOGGLE_CONFIG` | `toggles.yml`(模块总开关) |

### 5.6 任务调度(`Tasks` / `TaskManagers`)
`Tasks.scheduleDelayed` / `scheduleRepeated` / `scheduleTask` 都跑在游戏 tick 上,
不是独立线程。

### 5.7 移动管道(`LegalMovementManager`)
要让模块介入玩家移动(速度、鞘翅、stepheight 等),实现 `MovementModifier` 并注册进
`MovTasks.PLAYER_PIPELINE_0`。详见 `模块.md` 第 11 节。

## 6. 模块分组

功能模块按分组组织,每个分组由一个 `ModuleGroup` 承载,分组的初始化写在对应的 `*Tasks.java` 里
(`MineTasks` / `ChatTasks` / `RenderTasks` / `CombatTasks` / `InvTasks` / `MovTasks` /
`InteractionTasks` / `SurvivalTasks` / `SlimefunTasks` / `ModelTasks` / `ExtraTasks` / `MainTasks`)。

注册一个分组:

```java
public static final ModuleGroup moduleGroup = new ModuleGroup("Mine");

private static void initModules(ModuleManager m) {
    mineExtra = new MineExtra().register(m);
    mineBot = new MineBot().register(m);
}

static {
    moduleGroup.registerFactories(MineTasks::initModules);
    HackModules.registerModuleGroup(moduleGroup);
}
```

`ModuleGroup` 继承 `ModuleManager`,内部惰性加载:`registerFactories` 只是把初始化函数存起来,
真正 `new` 出模块实例是在 `loadModules()` / 重载时。

## 7. 26.x 上必须注意的硬约束

1. **物品组件绑定前不能构造 `ItemStack`**
   `Items.X.builtInRegistryHolder().components()` 在 items 注册表绑定前会抛
   `IllegalStateException: Components not bound yet`。静态字段里不要直接 `new ItemStack(...)`,
   要么放到首次 tick 后,要么用懒加载 + `areComponentsBound()` 守卫。
2. **自己创建的线程池必须是守护线程**
   否则客户端退出时 JVM 被非守护线程卡住,`ClientShutdownWatchdog` 超时崩溃。
   统一用 `me.matl114.utils.ThreadUtils.daemonThreadFactory("前缀")`。
3. **渲染是两阶段的**
   `render*` 已拆成 `extract*`(提交渲染状态)+ 真正的绘制。
   涉及渲染的改动要先确认自己挂在哪个阶段;HUD 的挂载点两版不同(见 §8)。
4. **Mixin 约束**
   类级 `@Mixin` 注解不能漏;`@Shadow` 不能依赖继承;Mixin 类里不要有非 private 静态字段;
   `@ModifyExpressionValue` 签名要完全一致;`@At` 目标必须存在于被注入方法体内;
   可选依赖用 `@Pseudo`。

## 8. 26.1.2 与 26.2 的 API 差异

绝大部分代码两版通用,下面这些是**动手前必须知道**的差异(以 26.1.2 为准,括号里是 26.2 的写法)。

### 8.1 GUI / HUD

| 26.2 | 26.1.2 |
|------|--------|
| 有独立的 `net.minecraft.client.gui.Hud` 类,HUD 的 `extract*` 都在它上面 | **没有 `Hud` 类**,那些方法直接在 `Gui` 上(`extractRenderState` / `extractTabList` / `extractCameraOverlays` / `extractSpyglassOverlay` / `extractTextureOverlay` / `extractPortalOverlay` / `extractVignette`,都是 private) |
| `Gui.hud.chat` | `Gui.getChat()`(`chat` 字段是 private 但公开了 getter) |
| `Gui.screen()` / `Gui.setScreen(...)` / `Gui.handleKeybinds()` / `Gui.overlay()` | 这些都在 `Minecraft` 上:`Minecraft.screen`(public 字段) / `Minecraft.setScreen` / `Minecraft.handleKeybinds` / `Minecraft.getOverlay()` |
| `GuiRenderState.isHudHidden` | `GameRenderer.getGameRenderState().optionsRenderState.hideGui` |
| `Gui.clientLevelTeardownInProgress` | `Minecraft.clientLevelTeardownInProgress` |
| `Hud.getMobEffectSprite(...)` | `Gui.getMobEffectSprite(...)` |

### 8.2 渲染

| 26.2 | 26.1.2 |
|------|--------|
| `net.minecraft.client.renderer.extract.LevelExtractor` | 没有这个包/类,提取在 `LevelRenderer.extractLevel(...)`,实体在 `LevelRenderer.extractEntity(...)` |
| `LevelRenderer.submitFeatures(...)` | 没有该方法;最后一个提交动作是 `LevelRenderer.submitBlockDestroyAnimation(...)` |
| `Minecraft.levelExtractor` | `Minecraft.levelRenderer` |
| `GameRenderer.mainCamera()` | `GameRenderer.getMainCamera()` |
| `GameRenderer.mainRenderTarget()` | `Minecraft.getMainRenderTarget()` |
| `GameRenderer.nightVisionScale(...)` / `lighting()` | `getNightVisionScale(...)` / `getLighting()` |
| `GuiRenderer.render()` | `GuiRenderer.render(GpuBufferSlice)`,传 `fogRenderer.getBuffer(FogRenderer.FogMode.NONE)` |
| `ScreenEffectRenderer.submitBlockSprite/submitWater/submitFire` + `SubmitNodeCollector` | `renderTex/renderWater/renderFire` + `MultiBufferSource` |
| `WeatherEffectRenderer.extractRenderState(ClientLevel, float, Vec3, WeatherRenderState)` | `extractRenderState(Level, int ticks, float, Vec3, WeatherRenderState)` |

| 26.2 | 26.1.2 |
|------|--------|

### 8.4 回退时最容易踩的坑:`@At` 的 `ordinal`

把 `@At` 的 `target` 换成另一个类/方法之后,**必须重数 `ordinal`** ——
它数的是**字节码里匹配该 target 的指令序号**,源码长得一样也不代表序号没变。

两个实例:

- `Minecraft.handleKeybinds` 里的 `setScreen` 调用:26.2 只有背包一处(ordinal 0),
  26.1.2 前面多了社交界面 → 背包变成 **ordinal 1**
- `Minecraft.setScreen` 里对 `screen` 字段的访问:**getfield 和 putfield 一起编号**,
  依次是 判空/removed/**赋值**/判空/added → 赋值那次是 **ordinal 2**,不是 0

编译期完全不查这个;mixin 只要序号在范围内也不会报错,只会静默作用到错的位置。
用 `javap -c -p` 数官方 jar 的字节码,别用源码数。
